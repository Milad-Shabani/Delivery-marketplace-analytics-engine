# Dashboard Guide

The dashboard exists in two languages, built from one template:

| Version | File | URL (GitHub Pages) |
|---|---|---|
| English | `dashboard/index.html` | `https://milad-shabani.github.io/Delivery-marketplace-analytics-engine/` |
| فارسی (RTL) | `dashboard/fa/index.html` | `https://milad-shabani.github.io/Delivery-marketplace-analytics-engine/fa/` |

Both are static pages (Plotly.js from jsDelivr; no server needed, they also work
via `file://`). They read `dashboard/data/dashboard_data.js`, a plain
`window.DASHBOARD_DATA` object generated by `scripts/build_dashboard_data.py`.
A language switch in the header and a link in the footer connect the two.

## Rebuilding

```bash
python scripts/run_pipeline.py          # data/raw + data/processed (incl. KPI layer)
python scripts/build_dashboard_data.py  # dashboard/data/dashboard_data.js
python scripts/build_excel.py           # outputs/excel/Company1_Business_Analytics.xlsx
python scripts/build_dashboards.py      # dashboard/index.html + dashboard/fa/index.html (+ outputs/dashboard/)
```

## How the two versions are built

```
src/dashboard/template.html        layout, CSS, chart code (language-neutral)
src/dashboard/i18n/en.json         English strings
src/dashboard/i18n/fa.json         Persian strings
scripts/build_dashboards.py        renders both pages, validates the string files
```

Edit the template or the JSON files — never the generated HTML. The build
fails if the two JSON files have different keys or `{placeholders}`, if the
template needs a string that is missing, or if the data contains a city,
channel, cuisine, … that has no translation (`tests/test_dashboards.py` runs
the same checks).

Persian specifics: right-to-left layout with CSS logical properties,
Vazirmatn FD (Latin digits are drawn as Persian digits), Persian decimal and
thousands separators and the Persian percent sign, numbers isolated with
`unicode-bidi`, Persian-script Gregorian month names on date axes, and the
city names transliterated (the cities are fictional).

## Sections

| Section | What it answers |
|---|---|
| Executive overview | 34-KPI scorecard in seven groups (value, change vs. previous month, 12-month sparkline, definition on hover); GMV/orders trend; city profit ranking |
| Financial performance | Contribution margin before vs. after promotions, revenue mix, cost structure, margin-driver decomposition |
| Unit economics | Per-order waterfall (revenue → contribution → after promotions), revenue vs. cost to serve, margin by cuisine, restaurant tier and payment method |
| Customers | Snapshot tiles, new vs. returning, month-1 retention, segments and their profit share, subscribers vs. non-subscribers, revenue concentration (Lorenz), cohort heatmap |
| Restaurants | Revenue-vs-margin quadrants, concentration tiles, supply (active restaurants, orders per restaurant) |
| Operations | On-time / very-late / cancellation / refund trends, weekday × hour demand heatmap, cancel reasons, city scorecard, rider utilization and productivity, vehicle table, rating by delay |
| Marketing & promotions | Observed spend by channel, blended CAC, assumed vs. observed CAC, observed LTV:CAC, promotion intensity, promoted vs. non-promoted orders |
| Forecast & plan | 12-month forecast with 80 % interval, model selection, strategic plan verdict |
| Optimization | Downside/base/upside scenarios, promotion-budget allocation |
| Sources | Methodology, KPI windows, limitations |

## Chart conventions

Two measures with different units are shown as two stacked panels sharing
the x axis (never a dual axis); every multi-series chart has a legend; colours
come from a validated categorical palette; heatmaps are single-hue.

## Visual design

- **Hero:** a dark-navy header with the headline, three fact chips and a "receipt" of the
  average delivered order (revenue, rider cost, payment processing, refunds, contribution,
  promotions, result after promotions). It is built from `unit_econ.waterfall` in the data
  payload, so it always matches the charts below it.
- **KPI scorecard:** every tile has a status bar (green = good move, red = bad move for the
  business, grey = flat), a change pill and a 12-month sparkline; hover for the definition.
- **Typography:** English uses Bricolage Grotesque (headings) and Instrument Sans (text) from
  Google Fonts; Persian uses Vazirmatn FD (Persian digits) from jsDelivr. If a font cannot load,
  the system font stack takes over and nothing breaks.
- **Layout:** pill navigation, white cards on a cool-paper background, insight call-outs with an
  inline-start accent (flips automatically in RTL), and a single-column layout below 980 px.
- **Motion:** the receipt "prints" on load; this is disabled under `prefers-reduced-motion`.

## Updating design tokens

Colors, fonts and spacing are CSS custom properties at the top of
`src/dashboard/template.html` (`:root { --deep: ...; --teal: ...; --font: ...; --display: ...; }`).
Font stacks come from the `meta_font_stack` / `meta_display_stack` strings in the i18n files and the
`<link>` tags are produced by `font_links()` in `scripts/build_dashboards.py`.
